## Грабли, найденные при разведке

Эти четыре пункта ломают наивный «скопировать как есть» и определяют порядок фаз.

1. **`CORS_ORIGINS` содержит номер старого проекта.**
   Текущее значение: `https://synapse.tel,https://skillswap-frontend-1002061524854.europe-west1.run.app`.
   Номер `1002061524854` в новом проекте другой. Значение обязано быть переписано
   на новый URL фронтенда. Кривой `CORS_ORIGINS` роняет gin-contrib/cors паникой
   на старте — сервис не поднимется вообще. Из-за этого `skillswap-api` деплоится
   **дважды**: первый раз в фазе 0 с временным значением, второй раз в фазе 1 с
   финальным, когда URL фронтенда уже известен.

2. **`DATABASE_URL` содержит connection name старого инстанса.**
   Внутри секрета — путь к Unix-сокету вида
   `/cloudsql/project-8aff5131-25d9-4667-85c:europe-west1:skillswap-db`.
   Секрет нельзя скопировать байт в байт: строку надо пересобрать под
   `synapse-prod:europe-west1:skillswap-db`. Пароль и имя БД переносятся без изменений.

3. **У `skillswap-api` задублированы тома с секретами.**
   `google-credentials-json` примонтирован дважды, `google-token-json` тоже дважды —
   четыре тома вместо двух, наследие повторных `--update-secrets`. В новом проекте
   монтируем по два, в разные подкаталоги (`/secrets/google-cred/` и
   `/secrets/google-token/` — два секрета не могут монтироваться в один каталог).

4. **Доменов четыре, а не три.** `tapreview.space` принадлежит `google-review-nfc`,
   это отдельный продукт, не связанный с synapse, его исходники лежат вне репозитория
   `irpen` и вне git. Инвентаризация «по репе» его пропускает.

5. **`gcloud secrets` на Windows портит значения с переводами строк.**
   Обнаружено при переносе: `gcloud secrets versions access` переводит `\n` в `\r\n`
   на выводе (текстовый режим stdout Windows), поэтому связка
   «`access` в файл → `create --data-file`» добавляет по байту `\r` на каждый перевод
   строки. `google-token-json` приехал как `}\r\r\n` вместо `}\r\n`.
   `google-credentials-json` уцелел только потому, что не заканчивается переводом строки.
   Сверка контрольных сумм через тот же `access` этого **не видит**: искажение
   симметрично и на чтении с обеих сторон.
   Правильный способ — REST API Secret Manager, он отдаёт и принимает base64 без
   трансляции:
   `GET  https://secretmanager.googleapis.com/v1/projects/<p>/secrets/<s>/versions/latest:access`
   `POST https://secretmanager.googleapis.com/v1/projects/<p>/secrets/<s>:addVersion`
   Любая сверка секретов должна сравнивать base64 из API, а не вывод `access`.

6. **Запятые и разделители в аргументах gcloud на Windows.** Правило «деплоить из
   PowerShell, а не из Git-Bash» верно, но недостаточно. PowerShell сам разбирает
   незакавыченную запятую как разделитель массива и склеивает части пробелом, из-за
   чего `--set-secrets=A=a:latest,B=b:latest` приезжает в gcloud как
   `Invalid secret spec 'a:latest B=b:latest'`. Любой аргумент с запятой должен быть
   закавычен целиком: `"--set-secrets=…"`.
   Для значения, которое само содержит запятые (`CORS_ORIGINS`), нужна форма gcloud
   с пользовательским разделителем `^X^`. **Разделитель обязан не встречаться ни в
   одном значении**: попытка взять `^@^` провалилась, потому что `@` есть в
   `SMTP_EMAIL=<smtp-отправитель>`, и gcloud разрезал строку по нему
   (`Bad syntax for dict arg: [gmail.com]`). Рабочий вариант здесь — `^#^`.

Дополнительно, из прошлого опыта проекта:
- Деплой и обновление Cloud Run запускать **через PowerShell, не через Git-Bash**:
  MSYS уродует пути `/secrets/...` и значения с запятыми (`CORS_ORIGINS`), что уже
  приводило к `panic: bad origin` на старте.
- Не использовать `--to-revisions` для переключения трафика: это пиннит сервис на
  ревизию, после чего `gcloud run deploy` молча отдаёт новой ревизии 0% трафика.
  Только `--to-latest`.

8. Проверить по прямым `*.run.app` URL, что сервисы живые. API на этом этапе отвечает

### Фаза 1 — окно обслуживания

1. Остановить запись на старом `skillswap-api`. Важно погасить не только HTTP, но и
   Telegram-бота с внутренним пятиминутным кроном — они живут в том же процессе и
   продолжат писать в старую базу после снятия дампа, из-за чего эти записи потеряются.
   `--max-instances=0` для этого не годится: Cloud Run требует max-instances не меньше 1.
   Рабочий способ — снять `allUsers` с invoker и выставить `--min-instances=0`.
   Без входящих запросов Cloud Run гасит инстанс примерно через 15 минут независимо от
   фоновой активности; фоновые горутины при этом убиваются, что здесь как раз нужно.
2. **Дождаться фактической остановки** и только потом снимать дамп: убедиться по
   метрике `billable_instance_time`, что инстансов ноль, либо что в логах нет новых
   записей бота. Снимать дамп до этого момента нельзя — потеряем свежие записи.
3. `pg_dump` базы `skillswap` со старого инстанса (~72 МиБ, минуты).
4. Залить дамп в новый инстанс поверх прогнанных миграций.
5. Сверить количество строк по ключевым таблицам: старое = новое.
6. Передеплоить `skillswap-api` в новом проекте с финальным `CORS_ORIGINS`
   (грабля 1).
